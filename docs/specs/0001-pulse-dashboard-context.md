## 4b. Slice lexicon
- **Unit A:** flags=`--from`/`--till`/`--range`/`--status`; range presets=`this-week|last-week|this-month|last-month` (verbatim, same Monday-to-today / complete-prior-period semantics); status vocabulary=`active|delivered|closed|updated` (ticket-summarizer's category vocabulary, not `sprint-analyzer`'s `done`/`in_progress`/`todo` bucket names); date-field binding per status: `active`→ none unless a range is also given, then `updated`; `delivered`/`closed`→`resolved` with fallback to `closed` when `resolved` is absent; `updated`→`updated`; 2+ distinct categories→`updated`; clock source=`today` (already cached at Bootstrap in `sprint-status-reporter.md`, never re-derived).
- **Unit B:** tag source field=`SprintItem.labels` (`string[]`); bucket vocabulary being replaced/extended=`delivered`/`in_progress`/`currently_at_risk`/`newly_at_risk` (`dashboard-composer.md`'s four fixed keys; `dashboard-page.html`'s `BUCKETS` array); per-tile counts=active vs closed (exact field names not yet decided — the plan must name them, e.g. `active_count`/`closed_count`, following `metrics model`'s existing `count`/`points` naming style rather than inventing new casing).

## 4c. Slice traps
- **Unit A:** (1) do NOT filter only `items` (current) while leaving Phase D1's baseline (snapshot-read or history-reconstructed) unfiltered — an asymmetric filter makes `delta-analyzer`'s shipped/newly_blocked/newly_stale comparisons incoherent (an item excluded from `current` but present in `baseline` reads as `removed` when it should simply be out of scope). (2) do NOT re-derive `today` a second time; Bootstrap already caches it (mirrors 0002's Unit-A-equivalent trap). (3) do NOT invent a different flag shape or vocabulary than `ticket-summarizer`'s — the task explicitly requires mirroring, and any drift (e.g. `--period` instead of `--range`, or `todo`/`done` instead of `active`/`delivered`/`closed`/`updated`) is a lexicon violation. (4) do NOT silently default an unrecognized `--range`/`--status` value; ticket-summarizer's convention is a hard validation stop naming the accepted set, before any fetch. (5) do NOT push the new filter into `getSprintItems` — it has no such parameter (`verbs.md`); filtering is client-side, after fetch, before `sprint-analyzer`.
- **Unit B (schema gap, critical):** (1) do NOT assume `sprint-analyzer`'s current per-item output already carries `labels` — confirmed absent from `completed`/`in_progress`/`at_risk`/`up_next` entries in its Output section. Plumbing `labels` through (widen `sprint-analyzer`'s per-item shape, most consistent with "the analyst owns bucket-adjacent facts") vs. passing raw `items` into `dashboard-composer`'s Phase P2 call (a bigger contract change, since that skill currently only ever sees already-computed models) is an open design decision the plan must make explicitly, not default silently. (2) do NOT compute "active vs closed" directly from raw `state` inside `dashboard-composer` — reuse `stateCategory`/`policy.state_categories` the same way `sprint-analyzer` already does; re-deriving a bucket from raw state is the exact anti-pattern `ARCHITECTURE.md` §7 and `dashboard-composer.md`'s Anti-patterns both forbid. (3) do NOT hardcode a fixed tile count in `dashboard-page.html` — its `BUCKETS` array and every function keyed off it assume exactly 4 static entries; tag tiles are dynamic per project and must render from the payload. (4) do NOT drop `deck_text` parity — the current plain-text "Copy for deck" view mirrors the four buckets 1:1 (id-ascending order, `None.` for empty, blurb segment omitted when empty); a tag-tile layout needs an equivalent deck_text rule set, not a silently narrower one. (5) do NOT invent an "Untagged" fallback bucket without deciding it explicitly — no grouping-bucket precedent exists in this codebase; the closest analog is `sprint-analyzer`'s `unknown→todo`-with-warning fallback (a category-fallback pattern, not a UI-grouping one).
